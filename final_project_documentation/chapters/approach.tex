\chapter{Infrastructure and Deployment}\label{chap:Methodology}

In this chapter, we explain how we provisioned the OKE cluster, how our code
changes reach running pods, and how we deploy and configure the system.

\section{Terraform Module Structure}\label{sec:manual-console-build}
We structured the root module (\texttt{Terraform-\allowbreak code/\allowbreak main.tf}) around two child modules,
\texttt{network} and \texttt{oke}, resolves the latest Oracle Linux 8 image for the
chosen compute shape, and provisions one OCIR repository per microservice from a
single \texttt{for\_each} over \texttt{local.microservices}. State is stored in an
S3-compatible OCI Object Storage backend (\texttt{providers.tf}), not locally. The
cluster runs Kubernetes v1.34.2, set explicitly in the \texttt{oke} module call.

\section{Configuration Patterns}\label{sec:analytical-framework}
We declared every NSG ingress and egress rule, for every subnet, once as data in
\texttt{modules/\allowbreak network/\allowbreak locals.tf} (\texttt{ingress\_by\_nsg}, \texttt{egress\_by\_nsg}),
then flattened into one map keyed by \texttt{"<subnet>-<index>"} so a single
\texttt{for\_each} generates every \texttt{oci\_core\_network\_security\_group\_\allowbreak
security\_rule} resource:

\begin{lstlisting}[caption={\texttt{modules/network/locals.tf} -- flattening per-subnet rule lists into one for\_each-able map}]
ingress_rules_flat = merge([
  for nsg_key, rules in local.ingress_by_nsg : {
    for idx, rule in rules :
    "${nsg_key}-${idx}" => merge(rule, { nsg_key = nsg_key })
  }
]...)
\end{lstlisting}

Therefore, adding a rule only requires one new object in \texttt{ingress\_by\_nsg} or
\texttt{egress\_by\_nsg}; the resource block itself never changes. The same pattern
builds the four subnets and their NSGs from typed maps rather than one block per
subnet.

\section{CI/CD Pipeline}\label{sec:evaluation-criteria}
We configured each of the five application repositories with its own \texttt{ci.yml} workflow,
triggered on push to \texttt{main}. All five follow the same template: a
multi-architecture image build (\texttt{linux/amd64}, \texttt{linux/arm64} via
Docker Buildx and QEMU), OCIR authentication through a short-lived OCI CLI token,
and a push tagged with both the GitHub Actions run number and \texttt{latest}.
Moreover, the \texttt{arm64} target matches the OKE node pool itself: \texttt{node\_shape}
defaults to \texttt{VM.Standard.A1.Flex}, an Ampere ARM64 compute shape, so every
image needs an ARM64 variant to run on the cluster's worker nodes.
We summarise how a code change reaches the running
cluster.

\section{Infrastructure Bootstrap Pipeline}\label{sec:bootstrap-pipeline}
We created \texttt{Terraform-\allowbreak code/\allowbreak .github/\allowbreak workflows/\allowbreak deploy.yml} to provision the environment from
a clean account. Triggered manually (\texttt{workflow\_dispatch}) rather than on
push, it runs, in order: \texttt{terraform apply}; extracts the new cluster's OCID
and load balancer subnet OCID from the Terraform output; generates a kubeconfig
from that cluster OCID; installs the NGINX Ingress Controller via Helm, passing
the load balancer subnet OCID through the
\texttt{service.\allowbreak beta.\allowbreak kubernetes.\allowbreak io/\allowbreak oci-load-balancer-subnet1} annotation so OCI
knows where to attach the Load Balancer; installs cert-manager and a
\texttt{letsencrypt-prod} \texttt{ClusterIssuer} (HTTP-01, using the
\texttt{ADMIN\_EMAIL} secret as the ACME registration email) so the ingress's TLS
certificate is issued automatically; creates the \texttt{ocir-secret} and
\texttt{app-secrets} Kubernetes Secrets from encrypted GitHub Actions secrets;
installs ArgoCD from its upstream manifest; and applies
\texttt{argocd/\allowbreak ecommerce-app.yaml} and \texttt{argocd/\allowbreak argocd-ingress.yaml}. The
kubeconfig step runs before any \texttt{helm}/\texttt{kubectl} command that
depends on it. Together, these steps assemble the full stack: infrastructure,
ingress controller and TLS, secrets, and the GitOps controller. Because Terraform
state lives in the S3-compatible OCI backend rather than on the runner, re-running
the workflow updates the existing infrastructure instead of provisioning a duplicate VCN or
cluster.

\section{Container Images and Health Checks}\label{sec:container-build}
We built every backend service from the same two-stage Dockerfile pattern, shown
here for \texttt{auth-service}. We selected \texttt{node:20-slim} for all five images rather
than an Alpine base: the OKE node pool runs ARM64, and cross-compiling Alpine
images for \texttt{arm64} under QEMU produced \texttt{Illegal instruction} crashes
at runtime, which the Debian-based slim image does not have.

\begin{lstlisting}[language={}, caption={\texttt{auth-service/Dockerfile}}]
FROM node:20-slim AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci || npm install
COPY . .

FROM node:20-slim AS runner
WORKDIR /app
ENV NODE_ENV=production
COPY --chown=node:node --from=builder /app /app
USER node
EXPOSE 5001

HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD wget --no-verbose --tries=1 --spider http://localhost:5001/health || exit 1

CMD ["npm", "start"]
\end{lstlisting}

For \texttt{ecomm-ui}, we used a three-stage variant (\texttt{deps}/\texttt{builder}/\texttt{runner})
that produces a Next.js standalone build, running as a dedicated \texttt{nextjs}
user (UID 1001) rather than the base image's built-in \texttt{node} user. Both
Dockerfile families run as non-root and expose a Docker-level
\texttt{HEALTHCHECK}.

We summarise the Kubernetes liveness and readiness probe timing
from the Helm chart's templates. The four backend services share identical timing;
\texttt{ecomm-ui} uses longer, more forgiving timing against \texttt{/} rather than a
dedicated health endpoint, to give its Next.js server-side rendering enough room to
finish a cold start on the ARM64 node pool before Kubernetes restarts or
deregisters the pod.

\section{Deployment Guide}\label{sec:deployment-guide}
We based the steps below on \texttt{Terraform-\allowbreak code/\allowbreak DEPLOYMENT.md}; they cover the
one-time setup of a new environment by hand; \texttt{deploy.yml}
(Section~\ref{sec:bootstrap-pipeline}) automates the same sequence. Once the
environment exists, ordinary code changes go through the per-push CI/CD path in
Section~\ref{sec:evaluation-criteria} instead, with no manual step in between.

\subsection*{Prerequisites}
Docker 20+, the OCI CLI, Terraform 1.5+, \texttt{kubectl} 1.28+, and Helm 3+,
installed locally.

\subsection*{Deployment Steps}
\begin{enumerate}[leftmargin=1.4em]
  \item \textbf{Authenticate to OCIR} using a short-lived OCI CLI token, or a static
        OCI Auth Token as a fallback.
  \item \textbf{Build and push all five images} with the repository's
        \texttt{scripts/build\_and\_push.sh <REGION> <NAMESPACE> <TAG> <COMPARTMENT>}.
  \item \textbf{Provision infrastructure:}
\begin{lstlisting}[style=shellstyle]
terraform init
terraform plan
terraform apply
\end{lstlisting}
  \item \textbf{Configure \texttt{kubectl}} via
        \texttt{oci ce cluster create-kubeconfig}, then apply the namespace:
\begin{lstlisting}[style=shellstyle]
kubectl apply -f ./kubernetes/00-namespace.yaml
\end{lstlisting}
  \item \textbf{Create the OCIR pull secret and application secrets.} The pull
        secret is a Kubernetes \texttt{docker-registry} Secret built from an OCI
        Auth Token; application secrets come from a local, gitignored \texttt{.env}
        file:
\begin{lstlisting}[style=shellstyle]
kubectl create secret docker-registry ocir-secret \
  --docker-server=jed.ocir.io \
  --docker-username='<OCIR username>' \
  --docker-password='<OCI auth token>' \
  -n ecommerce-ns

kubectl create secret generic app-secrets \
  --from-env-file=.env -n ecommerce-ns
\end{lstlisting}
  \item \textbf{Deploy the application} -- either the Helm chart (the path ArgoCD
        also reconciles against) or the raw manifests:
\begin{lstlisting}[style=shellstyle]
helm install ecommerce ./helm/ecommerce-app -n ecommerce-ns
% or, applying each raw manifest in numeric order (00 through 06)
\end{lstlisting}
  \item \textbf{Register the Application with ArgoCD} by applying
        \texttt{argocd/ecommerce-app.yaml}, so future pushes flow through the CI/CD
        pipeline instead of manual commands.
\end{enumerate}

\section{Testing}\label{sec:testing}
To strengthen quality assurance across our project, we created the dedicated
\texttt{EjadaStore-Testing} repository. We used it to run automated API,
security, and regression tests against our production deployment at
\url{https://shoy.publicvm.com}. During our initial QA cycle, we combined live
endpoint validation with source-code review and identified 15 opportunities for
improvement: six critical, five high, and four medium priority.

\subsection*{Testing Architecture \& Framework}
Our testing architecture employs industry-standard tooling structured across multiple layers:
\begin{itemize}
    \item \textbf{API \& Integration Testing:} Built with \textbf{Vitest} for high-speed concurrent execution, covering REST endpoints, request validation, and database state checks. The suite validates all four backend services (Auth, Products, Orders, Payments) as well as health checks.
    \item \textbf{End-to-End (E2E) UI Testing:} Implemented with \textbf{Playwright} to simulate real customer and admin browser interactions across the Next.js frontend, comprising 12 customer journeys and 8 admin journeys.
    \item \textbf{Continuous Integration (CI/CD):} Integrated via \textbf{GitHub Actions} (\texttt{qa-tests.yml}) to run automatically on code pushes, pull requests, and a daily schedule.
    \item \textbf{Security Testing Suite:} Dedicated test cases explicitly targeting NoSQL injection (e.g., email/password object injection), authentication bypass, and data integrity manipulation.
\end{itemize}
In total, the test framework comprises over 90 test cases distributed across 6 distinct test files, and can execute full API regression against the live production server in approximately 25-30 seconds.

\subsection*{Testing Recommendations \& Next Steps}
Based on the QA execution against the production environment, we established the following ongoing recommendations for the development team:
\begin{enumerate}
    \item \textbf{Prioritize Auth Middleware Fixes:} Ensure the Next.js BFF (\texttt{middleware.ts}) protects all \texttt{/api/admin/*} routes and mutative endpoints (\texttt{POST}, \texttt{PUT}, \texttt{DELETE}), rather than just the \texttt{/admin} UI pages.
    \item \textbf{Implement Server-Side Validations:} Enforce strict input validation at the service level (e.g., ensuring \texttt{quantity > 0}, \texttt{price >= 0}) to provide defense-in-depth regardless of frontend constraints.
    \item \textbf{Adopt Test-Driven Fixes:} Leverage the functional QA suite to verify code changes prior to deployment.
    \item \textbf{Secure Secrets:} Migrate plaintext Stripe and JWT secrets out of \texttt{docker-compose.yml} and into a secure secrets manager.
\end{enumerate}

\subsection*{Team Response to the Payment-Service Regression}
During remediation, we found that overlapping changes in the payments service temporarily
removed \texttt{server.ts} and its associated schema, which prevented the service
from running correctly. We identified the regression during coordination
and retesting. Ali Hamad restored the deleted payment-service files and corrected
the CORS allowlist, while Abdelrahman Darwish reconciled the server and schema
changes and pushed the consolidated update. Afterward, we tested the deployed service
again as part of the full production run. This recovery is recorded as a team
remediation activity rather than as a separate product defect because it occurred
while the original findings were being fixed.

pass rate of 98\%. We confirmed that all six critical security cases passed and
